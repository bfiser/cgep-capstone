# CGEP Capstone Write-up: Audit defense of Acme Health's Patient Intake API

## Primary framework: HIPAA Security Rule
Acme Health’s primary compliance framework is the HIPAA Security Rule.  Acme Health was considering three compliance frameworks in order to close eight compliance gaps in Acme Health's Patient Intake API.  If left unaddressed these gaps would lead to a failed audit.  The three choices were the HIPAA Security Rule, SOC 2 Type II, and CMMC Level 2.  When deciding between the three, SOC 2 Type II was not made a priority because only one customer was asking about it.  Also deprioritized was CMMC Level 2 because the federal pilot is on the table, but not confirmed.  The HIPAA Security Rule was selected because Acme Health is a telehealth company that handles data via a Patient Intake API.  The Patient Intake API handles Protected Health Information (PHI) and Electronic Protected Health Information (ePHI), and the HIPAA Security Rule's primary purpose is to establish a national set of security standards to protect the confidentiality, integrity, and availability of ePHI.  Finally when it comes to healthcare organizations that handle ePHI the HIPAA Security Rule isn't just a suggestion or set of guidelines it is a federal law and mandatory regulation.

## Design decisions

- **Region: us-east-2.** This was the region assigned when I created my AWS account for the labs, and it is enforced: the organization's service control policy denies EC2 actions in other regions (my first deploy attempt in us-east-1 was rejected). The HIPAA Security Rule has no data residency or geographic storage requirements, so I kept the assigned region.

- **Object Lock: GOVERNANCE mode, 60-day default retention.** GOVERNANCE balances evidence integrity with operational control. Standard users and automated workloads cannot delete or overwrite evidence before retention expires; only a principal explicitly granted `s3:BypassGovernanceRetention` can, and the pipeline's apply role is explicitly denied that permission. COMPLIANCE mode would make the evidence, and the bucket, undeletable by anyone until retention expires, which is a poor fit for a 30-day project in a sandbox account. Retention is counted per object from upload, so 60 days keeps even late-project evidence locked through the window between submission and grading. In production, I would use COMPLIANCE mode in a separate evidence account, and enable CloudTrail S3 data events on the vault so any retention bypass is recorded (the trail currently logs management events only).

- **Apply on merge vs. manual approval gate.** I chose apply on merge to meet the goal of an audit-defensible system within 30 days without slowing engineering down. Controls are enforced in front of `main` rather than after it: a repository ruleset requires a pull request and a passing `grc-gate` check, with no bypass (I verified this when my own direct push to `main` was rejected), and only merges to `main` can assume the apply role. Each merge then produces a Cosign-signed evidence bundle in the Object Lock vault, which serves as the tamper-evident record of what was deployed and why. The gate's effectiveness was validated in PR #16, which granted the intake Lambda `dynamodb:*`: the policy check failed with a HIPAA 164.312(a)(1) violation, Apply, Sign, and Upload were skipped, and the merge button was blocked. The trade-off is that no human approves a change before it reaches production; the ruleset requires zero approvals because this is a solo project and the policy gate acts as the reviewer. In production, I would add a required human approval before apply.

- **Single vs. separate account.** I used a single AWS account for the 30-day remediation window to avoid the overhead of AWS Organizations, cross-account role assumption, and cross-account bucket replication; the capstone brief also allows a single account. The risk is that a compromise of this account could reach the evidence vault. GOVERNANCE mode and the apply role's explicit denies reduce that risk, but a separate evidence account is the stronger design for production, because evidence would then live outside the account being audited.

- **Terraform vs. policy split.** GAP-01, 02, 03, 04, 05, and 07 are closed in Terraform and enforced by a policy; GAP-08 is partially closed, with access logging and throttling implemented and enforced, while WAF is deferred. Terraform fixes the current state, and the policy stops the gap from coming back, so each layer covers the other's blind spot. Fixes that can be expressed as separate resources live in `hardening.tf`, attached to the starter's resources by reference; fixes that must live inside a starter resource block (DynamoDB encryption, Lambda `vpc_config`, the Lambda IAM policy, API stage logging) are edited in `main.tf` and tagged by GAP ID. The coverage table above lists each gap's file and policy. Every policy was break-tested by reintroducing its gap. The clearest example was GAP-02: removing the DynamoDB key produced "No changes" in the plan, because the live table kept its key, but the policy still failed, because a fresh deploy from that code would have used an AWS-managed key. Exceptions: DynamoDB point-in-time recovery is implemented but not yet policy-enforced, GAP-06 is deferred, and GAP-08's WAF is deferred (see What I didn't get to).

- **Encryption keys.** One customer-managed key (`aws_kms_key.phi`) protects ePHI in both the uploads bucket and the DynamoDB table, with automatic annual rotation. One key is simpler to manage and audit; the trade-off is a shared blast radius, since a misconfiguration of that key affects both data stores, so production could use a key per data store. The evidence vault uses a separate key (`aws_kms_key.evidence`) for separation of duties: the pipeline needs to write evidence but never needs the key protecting patient data. Both keys use a 7-day deletion window, the AWS minimum, which suits a sandbox; production would use 30 days.

- **Pipeline identity.** GitHub Actions authenticates to AWS through OIDC, so no long-lived credentials are stored anywhere. There are two roles, split by event: a plan role that only pull request runs can assume (read-only, plus the state lock file), and an apply role that only runs on `main` can assume. The apply role uses AdministratorAccess, because writing a precise policy for every service Terraform manages was out of scope for 30 days. I mitigated this with the main-only trust, the policy gate in front of `main`, and explicit denies that override AdministratorAccess: the apply role cannot bypass Object Lock retention or delete evidence versions, and cannot use the PHI key to encrypt or decrypt. Because S3 and DynamoDB need that key to decrypt data, the pipeline cannot read patient data even with administrator rights. A scoped deploy policy is on my next-sprint list.

- **Policy design.** The policies read Terraform's `configuration` view (what the code says) rather than `planned_values` (what Terraform expects to exist). Planned values are often unknown at plan time: on a fresh deploy, and even on my deployed system, the green PR showed the Lambda's IAM policy as "known after apply" because it referenced a table with a pending change. To keep policy content verifiable, I rewrote the uploads bucket policy and the Lambda IAM policy from `jsonencode` into `aws_iam_policy_document` data sources, whose statements appear as constants in configuration. A policy document the gate cannot inspect fails closed. Each policy targets specific resources rather than every resource of a type, because some exceptions are deliberate (for example, the CloudTrail bucket uses SSE-S3). The gate also runs all 37 policy unit tests before evaluating the plan, so a policy that can no longer catch its own failing fixtures cannot pass the pipeline. 

- **OSCAL component.** `oscal/components/acme-health-intake.json` describes the governed system as one component with five implemented requirements, one per HIPAA standard the gaps map to; `oscal/profiles/cge-p-minimum.json` selects those five controls. No official OSCAL catalog exists for HIPAA, so, following the course primer, the source is NIST SP 800-66 Rev. 2 and each requirement carries its 45 CFR 164 citation as a prop. OSCAL control IDs cannot contain parentheses, so citations such as 164.312(a)(2)(iv) become tokens such as `hipaa-164.312-a-2-iv`, with the exact citation preserved in the prop. Each requirement lists the Terraform addresses and Rego packages that implement and enforce it, which completes the chain a reviewer can follow: gap, Terraform, policy, OSCAL, catalog. Evidence links are full `s3://` URIs to the signed bundle from run 38632599567, the latest run when the component was authored, because a commit's own pipeline run cannot be referenced from inside that commit. Both files pass `trestle validate`, run in a gitignored workspace so trestle's scaffolding stays out of the repository.

## How the pipeline produces evidence

**Trace of pull request #19 and its merge run, 38632599567** (commit 86b36db):

1. **PR opened:** `grc-gate.yml` assumed the read-only plan role via GitHub OIDC, saved a Terraform plan, and ran the policy gate (37 unit tests, then all 7 policies against the plan). It passed. A failing gate stops here and the ruleset blocks the merge, as in red PR #16.
2. **Merge to `main`:** the workflow assumed the main-only apply role, re-ran the plan and gate, and applied the exact saved plan that passed.
3. **Sign:** the run's evidence (plan, policy results, apply log, run metadata) was bundled, hashed with SHA-256, and signed with Cosign keyless signing, recorded in the public Sigstore log.
4. **Vault:** the bundle, hash, signature, and a receipt were uploaded to `s3://acme-health-intake-evidence-80633ffe/runs/38632599567/`, under Object Lock GOVERNANCE retention until 2026-12-13.

**Verify it:** `bash scripts/verify-evidence.sh 38632599567 --vault acme-health-intake-evidence-80633ffe --profile <profile>` prints `CHAIN INTACT`. The run's GitHub artifact contains the same signed bundle for verification without AWS access, and a one-byte tampered copy fails both the hash and signature checks.

## Trade-offs and what I'd do with another sprint
- **WAF on the API (GAP-08).** *Trade-off:* AWS WAF cannot be attached natively to an API Gateway HTTP API, which is what the starter ships. Adding one means converting to a REST API or placing Amazon CloudFront in front of the HTTP API, which changes the routing architecture and adds request and data transfer costs. Given the 30-day timeline, I deferred it and relied on compensating controls: stage throttling limits how hard anyone can hit the API, and access logging records every request. Neither inspects request content, so injection attempts or traffic from known-malicious sources are not filtered today. *Next sprint:* I would first estimate the cost of CloudFront and WAF against Acme's risk tolerance. If justified, I would put CloudFront in front of the API with an AWS WAF web ACL using AWS managed rule groups (core rule set, known bad inputs, IP reputation), then add a Rego policy that fails the pipeline if the distribution has no web ACL attached, so the protection can't silently regress.
- **AdministratorAccess on the apply role.** *Trade-off:* Writing a precise policy for every service Terraform manages was out of scope for 30 days, so the apply role uses AdministratorAccess, mitigated by main-only trust, the policy gate, and explicit denies on evidence tampering and PHI key use. *Next sprint:* I would replace it with a scoped deploy policy limited to the services this Terraform manages (S3, DynamoDB, Lambda, API Gateway, KMS, CloudTrail, CloudWatch Logs, EC2 networking, and IAM), to resources named with the `acme-health-intake-` prefix, and to us-east-2. To find the exact permissions needed, I would use IAM Access Analyzer to generate a policy from the apply role's activity recorded in CloudTrail. Because a role that can modify IAM can escalate its own privileges, I would also require a permissions boundary on any role the pipeline creates.
- **Single account and GOVERNANCE mode.** *Trade-off:* The workload and the evidence vault share one account, so a takeover of this account could reach the evidence, and GOVERNANCE mode allows a permission-gated bypass of retention. The trail also logs management events only, so a bypass would not currently be recorded. *Next sprint:* I would move the vault to a dedicated evidence account where the pipeline has write-only access (it can add evidence but never modify or delete it), auditors have read-only access, and no one from the workload account has administrative access. With evidence isolated, I would switch the vault to COMPLIANCE mode, so no one, including the account root, can delete evidence before retention expires, and enable CloudTrail S3 data events on the vault so every object-level action, including any retention bypass attempt, is recorded.
- **No human approval before apply.** *Trade-off:* Changes that pass the policy gate deploy automatically on merge; the ruleset requires zero approvals because this is a solo project. *Next sprint:* Once Acme has more than one engineer, I would require at least one pull request approval and add a GitHub environment with required reviewers, so the pipeline pauses after the policy check and waits for a human before applying. Policy failures are already blocked automatically, so the reviewer would focus on what policies cannot judge: the plan summary, especially resource deletions or replacements, IAM changes, and anything not described in the pull request. The pipeline would surface that summary from the run's evidence so the reviewer sees only what matters.
- **Log encryption under AWS-managed keys.** *Trade-off:* The CloudTrail bucket uses SSE-S3 and the API access log group uses CloudWatch's default encryption, because using a CMK for either requires a custom key policy granting that AWS service access to the key. CloudTrail's log file validation provides tamper evidence, but neither log store's encryption is under Acme's custody. *Next sprint:* I would prioritize the API access log group, because its records include source IP addresses, a HIPAA identifier, for an endpoint that only serves patient intake. I would encrypt it with a customer-managed key whose key policy grants the CloudWatch Logs service access only for this log group, then do the same for the CloudTrail trail. As with the other controls, I would add policies that fail the pipeline if either log store loses its customer-managed key.
- **OSCAL catalog not machine-resolvable.** *Trade-off:* No official OSCAL catalog exists for HIPAA, so, following the course primer, the component cites NIST SP 800-66 Rev. 2 as its source and carries each 45 CFR 164 citation as a prop. Because 800-66r2 is a PDF guide, tools cannot automatically resolve the profile against it. *Next sprint:* I would map each of the five HIPAA standards to NIST SP 800-53 Rev. 5 controls using NIST's published crosswalks, and add a second control implementation sourced from the official 800-53 OSCAL catalog, keeping HIPAA as the declared primary. The same mapping would let Acme reuse this component for SOC 2 (commonly mapped to 800-53) and CMMC Level 2 (built on NIST SP 800-171), instead of rebuilding it per framework.
- **Controls without a policy.** *Trade-off:* Two controls are implemented but not enforced by the gate. DynamoDB point-in-time recovery was deployed through the green pull request but has no policy, and the "no request bodies in access logs" decision is not policy-checked, because the log format is a `jsonencode` call that appears empty in Terraform's configuration view. *Next sprint:* For point-in-time recovery, I would add a policy following the GAP-02 pattern: read the table's configuration and fail unless `point_in_time_recovery` is enabled, which catches a removal in code even when the plan shows no change to the live table. For the log format, I would read `planned_values`, where the format string is fully known at plan time because it has no unknown inputs, decode it, and fail if it contains any field outside an allowlist of approved request metadata.

## What I didn't get to

- **GAP-06 (reserved concurrency, DLQ, X-Ray).** Deferred. GAPS.md maps it to SOC 2 and CMMC controls but not to the HIPAA Security Rule, my declared framework, so I prioritized the gaps with direct HIPAA mappings. 

- **WAF on the API (GAP-08).** Access logging and throttling are in place; the WAF is not, because attaching one to an HTTP API requires CloudFront or a REST API conversion. My plan is under Trade-offs.

- **A planned teardown process.** `make destroy` no longer works cleanly, because the evidence vault (Object Lock and a deletion-deny policy) and the CloudTrail bucket (`force_destroy = false`) are deliberately built to resist deletion. Decommissioning this environment would need an ordered, documented process: let vault retention expire or use the governance bypass deliberately, empty the protected buckets, then destroy the rest.
